**P17 → P18 → P19 → P20 → cierre de P16 (release)**. Sin más dudas abiertas: lo que Leo dejó

## Decisiones de proceso

- Merge a `main` al cerrar cada fase con el gate en verde, sin pedir OK.
- Tags `pNN-done`: se crean **y se pushean** al cerrar cada fase.
- Tags `v*` (releases): solo con OK escrito de Leo.
- Delegación **equitativa entre proveedores conservando calidad**: repartir entre Codex
  (`gpt-6-luna`/`gpt-5.6-luna`), Antigravity gemini y Kimi, sin sobrecargar ninguno; subir a
  `gpt-6-sol`/`gpt-6-astra` solo si el modelo no llega. Claude Code (83 % semanal) y OpenCode
  (56 %) quedan en reposo hasta que reinicien; Antigravity claude/gpt agotado (~50 h).
- Gate completo (`cargo xtask check`): al cerrar cada fase y tras pasos grandes *(orquestador)*.
- `SYMPHONY_LIVE=1` **autorizado**; se usa solo cuando un test live aporta algo que `fake-agent`
  no cubre, y se avisa antes *(orquestador: avisar, no pedir permiso cada vez)*.

## P17 · TUI (en curso)

### S4 · Mascota: mini piano de una octava
- **No** fuegos artificiales: un **mini piano de una octava que se toca solo** (las teclas se
  presionan), como si estuviera trabajando. Solo en el **chat principal**.
- Frases **con personalidad** (estilo «pondering»/«cogitating» de Claude Code), rotativas.
- Tick actual de 1 s (sin timer nuevo).
- **Configurable**: env `SYMPHONY_NO_ANIM` + opción en config; respeta `NO_COLOR` y terminales
  tontas (piano estático).
- Verificación: snapshots a 80/160, pruebas de degradación y de config.

### S5 · Shell en curso (solo lectura)
- Solo procesos **que lanzaron los agentes** (tests, builds); sin shell interactiva ni stdin.
- **Pestaña nueva** dentro de la vista del agente, con salida en vivo de solo lectura.
- IPC: se añade `agent.processes` + streaming de salida al daemon *(orquestador: streaming real,
  no solo logs persistidos, porque el paso pide «en vivo»)*.

### S6 · Vistas avanzadas
- Pantalla `status` **global** (todos los proyectos): actualizar ADR-0018 para dejarlo explícito.
- **Heatmap mensual tipo GitHub** (días × semanas, intensidad por tokens).
- Ramas de git: listar **y acciones** (cambiar, borrar).
- Avance de agentes en un plan (rama, tarea/fase, %).

### S8 · Renderizado rico del chat (antes del cierre)
- **Controlado**: el texto en blanco; títulos, bullets, destacados y tablas con colores distintos.
- Color por **heurística de la TUI** sobre la estructura markdown *(orquestador: es lo que implica
  la opción «controlado»; no hacen falta marcadores del agente ni protocolo nuevo)*.
- El contenido **también se guarda en el transcript**; los colores se recalculan al pintar, así
  que no se persiste estilo, solo texto.
- Sin parser de markdown nuevo si se puede resolver por líneas (títulos `#`, bullets `-`, tablas
  `|`, código ` ``` `); si hace falta dependencia, se justifica en STACK.

### S7 · Cierre de P17
- Después de S8: auditoría, bitácora, gate completo, merge `--no-ff` a `main`, tag `p17-done`
  pusheado.

## P19 · Orquestación automática

### S1 · Modelo de decisión (System One)
- **Backend por defecto: Laya** (322–421 M, multilingüe, el más popular).
- **Personalizable**: el usuario enchufa el que tenga instalado (Jev, open-source o propio) por
  config; Symphony solo define el contrato `estado + preguntas tipadas → decisiones tipadas +
  probabilidades` y un adaptador por backend (trait `DecisionModel`).
- **Umbrales de la cascada**: > 0.9 actúa solo; 0.6–0.9 pide confirmación; < 0.6 escala al LLM
  grande.
- **Forma de despliegue**: proceso local aparte (servidor Python de Laya) hablando con Symphony
  por IPC/HTTP local, para no meter Python en el core *(orquestador: es lo que permite Laya sin
  romper CONSTRAINTS A6/A8; el core sigue sin llamadas de red externas, solo loopback local)*.
- ADR nuevo con todo esto antes de implementar.

### S2–S5 · Perfiles, planeador, delegación, `/orchester`
- **S2 Perfiles**: el modelo de decisión (Laya) **elige qué modelos entran en cada perfil**
  (`@best-coding`, `@best-reasoning`, `@fastest`, `@cheap`, `@automatic`), al inicio de sesión y
  al cambiar de modelo, solo entre modelos con créditos.
- **S3 Planeador**: el plan por fases con tareas se genera **cuando el usuario lo pide o cuando
  se detecta trabajo grande** (no para un cambio pequeño).
- **S4 Effort**: tres niveles (barato / producido / razonado).
- **S5 `/orchester`** (nombre en inglés, como el resto de comandos): crea plan y agentes;
  **muestra el plan para aprobación antes de lanzar** *(orquestador: coherente con «controlado»
  y con la revisión humana en acciones de alto riesgo)*. Verificación: test L2 con fake-agents
  de punta a punta.
- **S6 Paridad con Claude Code**: prioridad = **agente que edita archivos y codifica bien**, y
  que responda bien; lista de capacidades contrastada, huecos como tareas.
- **S7 Cierre.**
