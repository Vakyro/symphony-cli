Symphony CLI
Flujo, vistas y ramas

Este documento describe cómo debería experimentarse Symphony desde el punto de vista del usuario: qué ve al entrar, cómo crea y controla agentes, cómo elige modelos, qué ocurre cuando un proveedor falla, cómo se muestran las esperas por recursos, cómo se revisan cambios y cuáles son todas las salidas normales y excepcionales del flujo.

CLI/TUI como experiencia principal Usuario siempre conserva control Agente persistente Modelo reemplazable Workspaces aislados Failover sin reexplicar Contexto recuperable Sin describir stack tecnológico

1. Objetivo de experiencia

La experiencia ideal de Symphony debe hacer que trabajar con varios agentes se sienta como operar un único entorno, no cinco herramientas diferentes. El usuario debe poder iniciar el proyecto, lanzar uno o varios agentes, observar lo que hacen, intervenir cuando quiera y continuar aunque cambie el modelo que ejecuta una tarea.

1

Un solo punto de entrada

Una terminal y una sesión de Symphony concentran agentes, tareas, proveedores, recursos, cambios y contexto.

N

Varios agentes

El usuario puede crear múltiples agentes sin tener que gestionar manualmente múltiples terminales o ramas.

0

Reexplicaciones deseadas

Si cambia el modelo o proveedor, el usuario no debe volver a narrar el proyecto desde cero.

Regla UX principal: Symphony debe explicar siempre qué está ocurriendo y por qué. Un agente puede esperar, cambiar de modelo, bloquearse o fallar, pero nunca debe parecer que “simplemente se congeló”.

2. Modelo mental que debe aprender el usuario

La interfaz debe reforzar cinco conceptos sencillos. Todo lo demás puede quedar escondido hasta que haga falta.

ConceptoCómo debe entenderlo el usuarioQué puede hacer
ProjectEl proyecto/repo donde está trabajando.Abrirlo, inicializar Symphony, consultar estado global.
TaskUna unidad concreta de trabajo.Crear, priorizar, bloquear, completar, cancelar.
AgentLa entidad persistente que “posee” una tarea.Enviar instrucciones, pausar, cambiar modelo, revisar cambios.
ModelEl ejecutor de IA actual del agente.Elegir uno exacto o dejar que Symphony seleccione por profile.
ProfileUna intención como @code o @fast.Delegar la elección de modelo a Symphony.
Mensaje conceptual: el usuario no “abre Claude” o “abre Codex”. El usuario crea un agente de Symphony y decide quién lo ejecuta.

Bifurcaciones globales

Proyecto nuevo para Symphony

Se muestra inicialización, detección de proveedores, autenticación necesaria y perfil de rendimiento.

Proyecto ya configurado

Symphony restaura sesión, agentes, tareas, worktrees y estados anteriores antes de mostrar Home.

Proveedor falla

El agente persiste. La interfaz muestra el fallo, la política de failover y el nuevo executor si procede.

Máquina bajo presión

Symphony reduce concurrencia o pone operaciones pesadas en espera, explicando siempre la causa.

4. Entrada, diagnóstico y onboarding

4.1 Vista: Launch

Es la primera pantalla al ejecutar Symphony. Debe durar lo mínimo posible y sólo mostrar lo esencial.

SYMPHONY Project detected: arete-mobile Checking project state... Checking providers... Restoring session... Ready.

Ramas posibles

Proyecto reconocido. Cargar estado y entrar directamente al Home.
Proyecto sin Symphony. Ofrecer Initialize, Open without setup o Exit.
No parece repo/proyecto. Mostrar ruta actual y ofrecer seleccionar otra carpeta o salir.
Estado previo inconsistente. Entrar a Recovery View antes del Home.

4.2 Vista: First-run Setup

Debe ser corta. No debe convertirse en un wizard de veinte pasos. Sólo recoge decisiones que son necesarias para empezar.

Confirmar proyecto. Nombre y ruta.
Detectar proveedores. Mostrar cuáles están disponibles y cuáles necesitan atención.
Elegir profile de rendimiento. Eco, Balanced, Performance o Custom.
Confirmar política de failover. None, same-provider o any.
Entrar al Home.

4.3 Vista: Provider Setup

EstadoMensajeAcciones
READYProveedor usable.Continuar.
LOGIN_REQUIREDEl CLI existe pero no hay sesión válida.Abrir login oficial · Saltar proveedor.
NOT_FOUNDEse proveedor no está disponible en la máquina.Ver instrucciones · Ignorar.
ERRORNo pudo verificarse.Reintentar · Ver detalle · Desactivar.
El usuario nunca debería estar obligado a configurar los cinco proveedores para usar Symphony. Debe poder empezar con uno y añadir otros después.

5. Vista principal: Home / Dashboard TUI

Es la vista a la que el usuario vuelve constantemente. Debe responder de inmediato cinco preguntas: ¿qué proyecto tengo?, ¿qué agentes existen?, ¿qué están haciendo?, ¿qué proveedor/modelo usa cada uno?, ¿mi máquina está bien?

Componentes de Home

Agent List

ID, estado, modelo actual y tarea. Debe permitir entrar directamente a cada agente.

Provider Strip

Resumen compacto de salud. Los detalles completos viven en Provider View.

System Strip

CPU, RAM y slots de trabajo pesado. Su propósito es explicar por qué el scheduler está limitando algo.

Command / Action Bar

Entrada principal para crear agentes, enviar comandos o navegar.

Estados de Home

Home vacío — ningún agente

Mostrar una acción dominante: Create first agent. También permitir abrir Tasks, Providers o Settings.

Home con agentes activos

Priorizar actividad actual y alertas que requieren intervención.

Home con agentes completados

Agrupar los completados, ofreciendo Review / Merge / Archive.

Home con problema crítico

Mostrar banner superior no intrusivo pero visible: proveedor sin auth, worktree inconsistente, conflicto pendiente o recovery requerido.

6. Crear agente: flujo completo

Crear un agente debe ser extremadamente rápido. El usuario puede dar una instrucción libre y opcionalmente decidir cómo se ejecutará.

NEW AGENT Task: > Fix refresh token rotation and add regression tests Execution: (•) @code ( ) Exact model ( ) Decide later Failover: (•) Any compatible provider ( ) Same provider only ( ) Disabled Priority: Normal [ Create agent ]

Flujo ideal

El usuario escribe la tarea.
Symphony propone profile/modelo o respeta el elegido manualmente.
Comprueba que existe al menos un executor elegible.
Crea agente, task, workspace aislado y checkpoint inicial.
Ensambla el contexto inicial.
El agente aparece inmediatamente en Home con estado visible.

Ramas

Profile automático. Symphony filtra modelos no disponibles y escoge entre los restantes.
Modelo exacto. Se respeta mientras esté disponible. Si no lo está, se muestra una decisión al usuario antes de iniciar.
Modelo exacto no disponible. Opciones: esperar, escoger otro, convertir selección a profile o cancelar.
No hay proveedores elegibles. Llevar a Provider Setup sin perder la tarea escrita.
No puede prepararse el workspace. Mostrar causa y permitir retry/cancel; no crear un agente “medio roto”.

9. Tareas, dependencias y milestones

9.1 Vista: Task Board / Task List

No necesita ser un Kanban visual permanente. La experiencia principal puede ser una lista filtrable que muestre estado, dependencias y agente.

TASKS READY T-12 Implement auth backend Agent #1 T-16 Responsive modal fixes Agent #2 WAITING_DEPENDENCY T-18 Integration tests waits for T-12, T-16 BLOCKED T-09 Merge auth changes conflict requires review DONE T-03 Database schema

9.2 Estados

BACKLOGREADYRUNNINGWAITINGBLOCKEDDONEFAILEDCANCELLED

9.3 Dependencias

Tarea tiene dependencias pendientes. No se ejecuta. La vista debe decir exactamente qué tareas la bloquean.
Todas las dependencias completadas. Pasa a READY automáticamente.
Dependencia falla/cancela. La tarea dependiente debe quedar BLOCKED y pedir decisión: replanificar, ignorar dependencia o cancelar.

9.4 Milestones

Los milestones son agrupaciones opcionales. Si requieren aprobación manual, cuando se completan sus tareas aparece una vista de Gate Review con resumen, tests, cambios y acciones: Approve, Request changes, Hold.

10. Recursos, scheduler y esperas

Esta parte debe ser visible cuando importa e invisible cuando todo funciona. El usuario no debería gestionar manualmente CPU/RAM en el flujo normal.

10.1 Vista: System / Resource Monitor

SYSTEM Profile: balanced CPU 61% / target 70% RAM 64% / target 70% Heavy slots 1 / 1 RUNNING Agent #2 unit tests WAITING Agent #4 build Reason: heavy slot occupied by Agent #2 [ switch profile ] [ inspect processes ]

10.2 Ramas del scheduler

Hay recursos. Operación inicia inmediatamente.
No hay slot. Agente entra a WAITING_RESOURCE y se muestra quién/qué ocupa el recurso.
Presión alta de RAM/CPU. Symphony reduce concurrencia según política y explica qué se pospuso.
Operación excede límites o queda colgada. Mostrar proceso, duración y opciones: keep waiting, stop operation, pause agent.

10.3 Vista: Performance Profile

PerfilIntención para el usuario
EcoPrioriza que la máquina se sienta libre.
BalancedEquilibrio por defecto entre velocidad y fluidez.
PerformanceMás concurrencia; el usuario acepta mayor carga.
CustomEl usuario decide límites y concurrencia.

11.1 Vista: Context Overview

11.2 Modos

ModoQué comunica al usuario
RawUsar la información sin optimización cuando sea posible; salida de emergencia.
SafeReducción mínima; conservar más detalle.
BalancedDefault recomendado.
AggressiveReducir más el handoff y depender más de retrieval.

11.3 Vista: Context Object

Cuando el usuario abre un objeto ctx://..., ve el original, su procedencia, qué agente lo generó y cuándo se usó. Debe poder buscar dentro sin tener que introducir todo en el contexto del modelo.

11.4 Ramas

Contexto suficiente. El nuevo executor comienza normalmente.
Executor pide detalle adicional. Recupera sólo el objeto o fragmento necesario.
Usuario sospecha que se perdió información. Cambia a Safe/Raw y reintenta el handoff.
Contexto inconsistente. Mostrar qué fuente entra en conflicto y permitir escoger current truth o revisar manualmente.

12.3 Quota display

La UI debe diferenciar KNOWN, ESTIMATED y UNKNOWN. Nunca inventar un porcentaje exacto.

13. Failover y handoff

13.1 Vista: Failover Event

AGENT #1 — EXECUTOR CHANGE Previous: Claude / Sonnet Reason: Quota exhausted Checkpoint: Available · 8 sec old Eligible replacements: 1. OpenAI / Sol 2. Kimi / ... 3. Google / Flash Policy: any Switching to OpenAI / Sol...

13.2 Automatic failover path

Provider failure is detected and classified.
Agent remains alive; task/workspace do not change.
Existing checkpoint is selected.
Eligible replacements are filtered.
Policy chooses replacement automatically.
Handoff is assembled.
New executor resumes the same agent.
History records the transition.

13.3 Manual decision branches

Failover disabled. Agent becomes BLOCKED/WAITING_PROVIDER and asks the user to choose.
No eligible replacement. Offer wait, enable another provider, change policy or stop.
Checkpoint may be stale. Show warning and let user choose latest checkpoint, rebuild from workspace or cancel.
Replacement cannot understand/continue. Offer stronger context mode, different model, retry from checkpoint or manual intervention.

13.4 User-visible continuity

La conversación puede marcar una separación visual:

── Executor changed: Claude / Sonnet → OpenAI / Sol
   Reason: quota exhausted
   Agent #1, task and workspace unchanged
   Handoff restored from checkpoint

Esto deja claro que cambió el modelo, no el agente.

14.1 Vista: Changes

CHANGES — Agent #2 Modified 4 files Added 1 file Deleted 0 files src/auth/service.ts +72 -18 src/auth/tokens.ts +31 -10 tests/auth.refresh.test.ts +44 -0 [ inspect diff ] [ validate ] [ review ] [ prepare merge ]

14.2 Vista: Merge Preflight

Antes de integrar, se resume si el agente está listo.

CheckEstado
Task completePass / warning
Required validationPass / fail
ConflictsNone / detected
DependenciesDone / pending
User policyApproval required / auto allowed

14.3 Ramas de merge

Todo correcto. Merge o queue integration.
Validation warning. Usuario decide re-run, review o continuar si la política lo permite.
Conflicto. Task → BLOCKED. Mostrar archivos en conflicto y opciones: resolve manually, assign review agent, abandon merge.
Dependencia no completada. No permitir integración final; dejar en WAITING_DEPENDENCY.

15. Validación y revisión

15.1 Vista: Validation

VALIDATION — Agent #1 Tier 1 Syntax PASS Format PASS Targeted lint PASS Tier 2 Typecheck PASS Targeted tests FAIL Tier 3 Not required yet Failure: auth.refresh.test.ts → expected 200, received 401 [ inspect ] [ send to agent ] [ rerun ]

15.2 Paths

Validation passes. Agent can move to COMPLETED / review / merge.
Targeted check fails. Result is fed back to same agent and task remains RUNNING/TESTING.
Heavy validation waits. Agent state explains scheduler queue.
Repeated failure. Offer retry limit reached → switch model, create review agent, block task, manual intervention.

15.3 Review Agent path

Desde un agente o merge preflight, el usuario puede crear un reviewer. El reviewer recibe sólo task, diff, tests y restricciones relevantes. Resultado: findings + recommendation, nunca merge automático salvo política explícita.

17. Configuración desde el punto de vista del usuario

La configuración debe organizarse por intención, no por internals.

Vistas de configuración

General

Comportamiento de inicio, confirmaciones y defaults.

Providers

Habilitar/deshabilitar, login, modelos visibles y reserva de cuota.

Routing

Modelo/profile por defecto, política de failover y sugerencias de cambio.

Performance

Eco/Balanced/Performance/Custom.

Context

Modo por defecto: raw, safe, balanced, aggressive.

Shared resources

Skills, MCPs, herramientas y su disponibilidad.

Validation

Qué gates son obligatorios antes de completar/integrar.

Safety

Qué acciones siempre requieren confirmación del usuario.

Regla

Las opciones avanzadas deben estar ocultas por defecto. El camino ideal debe funcionar con unos pocos defaults razonables.

20. Journeys completos de referencia

Journey A — Un solo agente, happy path

Usuario abre Symphony en un proyecto ya configurado.
Home muestra todos los proveedores saludables y cero agentes.
Usuario crea /spawn @code "implement auth".
Symphony escoge un modelo disponible y crea el agente.
Agent View muestra progreso, cambios y validaciones.
La tarea termina y pasa validación.
Usuario revisa diff.
Merge preflight pasa.
Usuario integra y archiva el agente.

Journey B — Tres agentes sin ralentizar la máquina

Usuario crea tres agentes para backend, UI y tests.
Los tres esperan respuestas de IA al mismo tiempo.
Agent #1 pide tests pesados y obtiene el slot.
Agent #2 pide build y entra a WAITING_RESOURCE con razón visible.
Agent #3 sigue leyendo/modificando archivos porque sus operaciones son baratas.
Terminan los tests de #1; el scheduler libera el slot.
#2 comienza automáticamente.
Home mantiene la máquina y las esperas comprensibles.

Journey C — Se agota el proveedor a media tarea

Agent #1 trabaja con Sonnet.
Checkpoint se actualiza continuamente.
El proveedor devuelve evidencia de cuota agotada.
Agent #1 permanece vivo; sólo cambia su estado a transición de executor.
Symphony filtra sustitutos según policy.
Ensambla handoff desde checkpoint y workspace.
Nuevo executor continúa.
El usuario ve una marca en History; no reexplica el proyecto.

Journey D — Conflicto entre agentes

Agent #1 y #2 trabajan en workspaces aislados.
#1 termina y se integra primero.
#2 llega a merge preflight y detecta conflicto.
Task #2 pasa a BLOCKED.
Conflict Review muestra archivos y opciones.
Usuario resuelve, asigna reviewer o aborta.
Después de resolver, revalidation y merge preflight vuelven a correr.

Journey E — Recovery tras cierre/crash

La sesión se interrumpe inesperadamente.
Al volver a abrir, Launch detecta estado previo.
Symphony reconcilia agentes, workspaces y checkpoints.
Agentes inconsistentes aparecen en Recovery Center.
El usuario decide restart, failover, pause o archive.
Vuelve al Home con estado coherente.

21. Reglas de diseño y comportamiento

1. Estado siempre explicable

No mostrar “waiting” sin explicar qué espera y de quién depende.

2. Usuario manda sobre selección explícita

Un modelo exacto nunca se reemplaza silenciosamente por optimización.

3. Failover no borra identidad

Cambia executor; no cambia agent, task, workspace ni historial.

4. Los errores no destruyen trabajo

Ante fallo, preservar cambios, checkpoint y contexto antes de ofrecer recuperación.

5. Defaults simples

El usuario debe poder empezar sin configurar routing, contexto o recursos manualmente.

6. Avanzado bajo demanda

Scores, eventos, objetos de contexto y procesos existen, pero no dominan la vista principal.

7. Performance visible sólo cuando importa

No saturar Home con métricas; mostrar detalle cuando hay presión o espera.

8. No falsa precisión

Cuotas, uso y estimaciones deben decir si son conocidas, estimadas o desconocidas.

9. Una misma lógica en CLI/TUI y GUI futura

Las vistas conceptuales y estados deben ser los mismos, aunque cambie la presentación.

10. Recovery es un flujo de primera clase

Crash, failover, conflicto y auth error no son casos marginales; son parte normal de un sistema multiagente.
